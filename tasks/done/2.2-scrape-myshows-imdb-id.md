- `docs/DATA_ANALYSIS.md §9` — myshows.me is reachable **direct** on the dev machine (no proxy), so a

- `docs/SCHEMA.md §5` — `staging_imdb_id` columns and the resumability rule
  (`imdb_id IS NULL AND error IS NOT NULL` rows are retried, resolved rows skipped).

- `docs/ARCHITECTURE.md §4/§5` — the `MyShows` named client carries proxy/throttle/User-Agent; the

## Do
- `MyShowsPageParser` (Infrastructure/Import, pure): regex `imdb\.com/title/(tt\d{7,8})/` taking the
  **distinct** match (a real page repeats the link to the same id); Kinopoisk from the rating-provider
  anchor `href="https://www.kinopoisk.ru/film/<digits>/"` (the `hd.kinopoisk.ru/film/<hex>` links are
  watch-ads for other shows). Two distinct IMDb ids ⇒ ambiguous ⇒ recorded as a failure, never guessed.
- `IMyShowsPageFetcher` seam + `MyShowsPageFetcher` over the `MyShows` named client: a transport failure
  is returned as `PageFetchResult(null, null, "transport: …")`, never thrown, so it is recorded
  differently from a 200-with-no-id page (SPEC R14).
- `ImdbIdScraper`: resumable (skip resolved, retry errored), capped by `MyShows.MaxRequestsPerRun`
  (0 = uncapped), lease-guarded (`scrape_myshows`, heartbeat renew, renewal-false ⇒ stop writing), and
  mirrors a resolved id onto `staging_show.imdb_id`. Failures are written as `http_status` + `error`.
- `ScrapeJob` public entry point; `ScrapeMyShows/Program.cs` passes it to `ShowsJobRunner`.

## Constraints
- Use the `MyShows` named client only. A transport failure is NOT "no IMDb id on this page" — they must
  land in different `http_status`/`error` values (R14).
- Resumable: never re-fetch a show whose `staging_imdb_id.imdb_id` is already set.
- The scraper is a bulk multi-transaction writer → it takes the `scrape_myshows` lease and stops on a
  lost renewal (ADR-028).
- Kinopoisk is best-effort enrichment; its absence is not a failure.

## Data-safety follow-up (user-raised, same step)
- Scraped ids are expensive (myshows is behind DDoS protection; re-requests risk a ban). Confirmed
  `staging_imdb_id` has **no FK to `staging_show`**, so `--reset` cannot cascade-delete them, and
  `ResetAsync` never touches that table.
- Gap found and fixed: after a `--reset`/`--stage` cycle the freshly-inserted `staging_show` rows come
  back with `imdb_id = NULL` and the scraper won't re-mirror them (already resolved ⇒ not re-fetched).
  `StagingImporter.StageAsync` now rebuilds the derived `staging_show.imdb_id` mirror from the
  authoritative `staging_imdb_id` (set-based `UPDATE … FROM`, zero requests). Regression test:
  `Reset_then_stage_remirrors_saved_imdb_ids_without_losing_them`.
