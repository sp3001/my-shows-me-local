# Step 3.2 — `AddShowToTrackingUseCase`

## Read
- `docs/STATE.md` — current state; this step consumes the mapper (1.5) and the provider (3.1), both done.
- `docs/IMPLEMENTATION_PLAN.md step 3.2` — acceptance criteria (below).
- `docs/DECISIONS.md` ADR-023 / ADR-024 — adding a show is Enrichment scoped to one show; untracking is
  a logical delete and re-adding clears `deleted_at` rather than inserting.
- `docs/SCHEMA.md §2` — `tracked_show.tvmaze_show_id` is a NOT NULL FK to `tvmaze_show`; `user_show` is
  1:1 with a shared PK; `tracked_show.tvmaze_id` is UNIQUE.
- `Shows.Application/UseCases/AddShowToTrackingUseCase.cs` — the use case is already written; this step
  registers it and proves it with the plan's integration test.
- `Shows.Tests/Integration/TvmazeShowMapperTests.cs` — the `DatabaseFixture` + Black Mirror payload +
  `SequentialIdGenerator` + the `tvmaze_show_id` shadow-property seeding pattern to reuse.

## Do
- Register `AddShowToTrackingUseCase` and `UntrackShowUseCase` in `AddShowsInfrastructure` (scoped — they
  share the scoped context with their repositories/mapper/UoW). No use case is registered today.
- Write the integration test (the plan's whole acceptance): add a show twice from a fixture, then
  add→untrack→add, asserting the row counts and the preserved history.
- **Fix whatever the test exposes.** Two orderings are suspect and must be checked against real failures,
  not assumed:
  1. The new-show path saves the `tracked_show` shell before the mapper writes the source row, but
     `tvmaze_show_id` is a NOT NULL FK — the first save may violate it. If so, the use case must satisfy
     the FK before that save (the mapper test seeds a `tvmaze_show` row + sets the shadow property; the
     use case likely needs the provider's payload written as a source row first, then the mapper's DTO
     overload so it does not re-fetch).
  2. The restore branch is reached only when `FindByTvmazeIdAsync` returns a row, but that method filters
     `deleted_at IS NULL` — so a soft-deleted show returns null and the use case falls to the new-show
     path, which would hit the UNIQUE `tvmaze_id`. The restore path needs a lookup that sees soft-deleted
     rows (the repository's `*IncludingUntracked` escape hatch, or a dedicated find).

## Acceptance criteria
- [x] Integration test adds a show twice from a fixture and asserts one `tracked_show` row, one
      `user_show` row, one `tvmaze_show` row, no duplicate episodes.
- [x] After marking an episode watched and re-adding, the mark and the original `category_id` are unchanged.
- [x] Add → untrack → add again: one `user_show` row, `deleted_at IS NULL`, the original `added_at`
      preserved, and every watch mark still present.

## Constraints
- The use case writes ONLY the `tracked_show` identity + ids and the `user_show` row. Every catalog field
  and every episode is the mapper's to fill (SPEC R11). It never writes `episode_watch`/`ui_season_state`.
- Re-adding must not reset the category or `added_at`, and must not insert a second `user_show` row
  (ADR-024). The episode ids were never regenerated, so the watch marks are already correct.
- The use case lives in `Shows.Application` — it must not reference EF/HTTP/MAUI/Newtonsoft. It composes
  the seams (`ICatalogProvider`, repositories, `IShowMapper`, `IIdGenerator`, `IUnitOfWork`).
- Do NOT run `--promote`. Do NOT touch the import/staging tables — this is the search-add path, not the import.
