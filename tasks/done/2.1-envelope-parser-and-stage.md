# Step 2.1 — Envelope parser and `--stage`

## Read
- `docs/STATE.md` — current state; Phases 0–1 are done, the staging tables + `v_staging_issues` exist.
- `docs/DATA_ANALYSIS.md §2` — the JSON-RPC envelope shape: category files are a single envelope,
  `episodes.json` is an array of envelopes; `totalEpisodes`/`watchedEpisodes` are entry-level siblings
  of `show`, while `title`/`year`/`totalSeasons` are inside `show`. Trim titles (trailing `\t`).
- `docs/DATA_ANALYSIS.md §4` — the batches: `60` empty (must not crash), `57` per-status totals
  (78/246/16/207, the cross-check), `59` later totals, `58` the 43 shows with `episodes[]` + `started`.
  The arrays are the **UNWATCHED** set.
- `docs/SCHEMA.md §5` — `staging_show` / `staging_episode` columns. `staging_show` has **no** `status`
  column (myshows vocabulary must not leak); `tvmaze_resolution` starts `'unresolved'`.
- `docs/IMPLEMENTATION_PLAN.md step 2.1` — acceptance criteria (copied below).

## Do
- `MyShowsEnvelopeParser` (Infrastructure/Import, System.Text.Json): parse a category envelope into
  `ParsedShow` records (trim `title`/`titleOriginal`), and parse `episodes.json` into `ParsedEpisode`
  records **only** from envelopes whose result entries carry an `episodes[]` array (batch 58), plus the
  batch-57 per-status counts for the cross-check. Tolerate empty `result` (batch 60) and the
  `episodes`-less shapes (57/59) without crashing.
- `StagingImporter` (Infrastructure/Import): `DryRun` parses and reports counts, writes nothing.
  `Stage` upserts `staging_show` (from the four category files) and `staging_episode` (from batch 58),
  **insert-if-missing keyed on `myshows_id`** so a re-run is a no-op and never clobbers a user's
  DB-Browser edits. `--reset` clears `staging_show` + `staging_episode` (the tables this job owns —
  not `staging_imdb_id`, which the scraper owns).
- `DataPaths.InputDirectory` (defaults to the base directory) so the read-only inputs resolve in one
  place. `IStagingImporter` registered scoped in `AddShowsInfrastructure`.
- `ShowsJobRunner` gains an optional `handler` so a job can do real work after the host is built; the
  five other jobs pass nothing and keep their shell behavior. `Import`'s `Program.cs` stays a one-liner
  that dispatches to `ImportJob` (flag parse → gated migrate → importer).

## Acceptance criteria
- [x] `--dry-run` prints exactly **78 / 246 / 16 / 207** and total **547**, matching `episodes.json`
      batch `57`.
- [x] After `--stage`, `staging_episode` contains exactly **43** distinct `show_myshows_id` values.
- [x] Batch `60` (empty `result`) does not crash the parse.
- [x] Titles are trimmed (a trailing `\t` in the export does not survive into `title_ru`).
- [x] `--stage` is idempotent on `myshows_id`: a second run inserts 0 new rows and changes nothing.
- [x] Record both numbers (547 and 43) in `LOG.md`.

## Constraints
- `staging_show.source_watch_status` ∈ {watching, later, cancelled, finished}; `source_file` is the
  filename. Do **not** carry the export's `status` ("Returning Series") into any staging column.
- `staging_episode` rows are the **unwatched** set — the column name lies; the semantics are load-bearing.
- `--dry-run` must not create or write the database (no migrate, no rows). Only `--stage`/`--reset` write.
- The default (no flag) is `--dry-run` — never write staging without an explicit `--stage`.
- Parser + importer live in Infrastructure (Application may not touch JSON/EF; the staging tables are
  Infrastructure-only). The job project wires flags only.
