# Step 2.3 — TVmaze id resolution (`/lookup?imdb=`)

## Read
- `docs/STATE.md` — current state; this step consumes the 546 staged shows that carry an `imdb_id`
  (541 scraped + 5 manual) and must NOT touch the one manual `tvmaze_id` (show 96144).
- `docs/SCHEMA.md §5` — `staging_show.tvmaze_id` (from `/lookup?imdb=`) and `tvmaze_resolution`
  (`scraped` | `manual` | `title_year` | `unresolved`). This step writes only those two columns.
- `docs/SCHEMA.md §6` — `v_staging_issues`: a `tvmaze_id IS NULL` row is `unresolved_tvmaze_id`/blocking.
  After this step, every show the lookup resolves leaves that blocking set; unresolved ones stay in it.
- `docs/IMPLEMENTATION_PLAN.md step 2.3` — acceptance criteria (below).
- `docs/DATA_ANALYSIS.md §8` fact 14 — `/lookup?imdb=` returns a **flat** show object (not the search
  score envelope); a 404 means "TVmaze has no show with that IMDb id".
- `docs/ARCHITECTURE.md §5` — one named client per host, throttle + Polly live there; the resolver must
  go through the provider (`ITvmazeShowSource`/`ICatalogProvider`), never build its own client (R14).
- `Shows.Infrastructure/Import/ImdbIdScraper.cs` — the structural template: resumable, capped,
  lease-guarded bulk writer. This step mirrors it over the TVmaze lookup seam.

## Do
- `TvmazeIdResolver` (Infrastructure/Import, internal, scoped) — the `--resolve` job body. For each
  staged show that has an `imdb_id` but no `tvmaze_id` yet, call the provider's
  `LookupByImdbIdAsync(imdbId)` and record the result in `staging_show`:
  - resolved → set `tvmaze_id` + `tvmaze_resolution='scraped'`.
  - 404 (provider returns null) → leave `tvmaze_id` NULL, set `tvmaze_resolution='unresolved'`.
  - transport failure (`TvmazeUnavailableException`) → **do not** mark unresolved; leave the row as-is
    (retry next run) and count it as failed. R14: a dead proxy is not "no data".
- **Resumable:** skip a show that already has a `tvmaze_id` (this protects the manual `tvmaze_id=86754`
  on show 96144 — it is never a target, so it is never overwritten). A show with `imdb_id` but
  `tvmaze_resolution='unresolved'` IS retried (a transient 404 or a TVmaze gap may resolve later).
- **Capped:** at most `Tvmaze.MaxRequestsPerRun` lookups per run (0 = uncapped), lowest `myshows_id`
  first, so an interrupted run resumes without one invocation hammering TVmaze.
- **Lease-guarded:** bulk multi-transaction writer → take the `resolve_tvmaze` lease, renew on the
  heartbeat; a renewal that returns false stops writing immediately (ADR-028).
- Wire `--resolve` into `ImportJob` (a DB-writing mode: migrates first, runs after stage/reset, before
  report so `--resolve --report` reports the post-resolution state). Add `MaxRequestsPerRun` to the
  `Tvmaze` section of `appsettings.json` (default 0 = uncapped; the throttle already serialises at 250ms).
- Register `TvmazeIdResolver` scoped in `AddShowsInfrastructure`.

## Acceptance criteria

- [x] Any `unresolved` row must appear in `v_staging_issues` as blocking (verified: the 7 unresolved

- [x] Tests against a fake provider seam, **no network** (5 tests: resolved->scraped, 404->unresolved,
      transport-failure->left-for-retry not unresolved, resumable skips a show with a tvmaze_id incl. the
      manual one, cap lowest-id-first, lease-refusal returns non-zero).
- [x] The manual `tvmaze_id=86754` on show 96144 is never overwritten (verified live: it has no imdb_id,
      so it was never a target; tvmaze_id=86754 intact after the run).

## Constraints
- The resolver writes ONLY `staging_show.tvmaze_id` and `tvmaze_resolution`. It must not write any
  mapped/source/user table — fetching+recording is its whole job (the mapper owns mapped rows, P3).
- It must call the provider through DI (`ICatalogProvider`/`ITvmazeShowSource`), never construct an
  `HttpClient` or inspect a URL to route (R14, ARCHITECTURE §4).
- A `TvmazeUnavailableException` is NOT a 404. Marking a transport failure `unresolved` would make a
  dead proxy look like "TVmaze has no data" and silently drop shows from tracking — the exact R14 bug.
- Do NOT run `--promote`. Do NOT re-run the scrape. The user considers the myshows scrape done.
- Back up `data/shows.db` before the live `--resolve` run (it writes the user's staging table).
